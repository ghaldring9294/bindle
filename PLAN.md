# Plan

Where bindle stands and what's next. The design and the reasons behind it are in [docs/design.md](docs/design.md); what changed in each version is in [CHANGELOG.md](CHANGELOG.md). Update this when work lands or priorities change.

## Where it stands (2026-11-24, v0.31.0)

- **The tool:** the commands in README's table (tests keep the README, `/bindle` and AGENTS.md in step with the CLI); one Python implementation shared by the CLI and every bindle's hooks; unit tests in CI (macOS, Linux and Windows) plus an end-to-end test against real Claude Code.
- **In use on three machines:** a personal laptop and a Windows PC with the personal bindle writable; a work machine with its domain bindle writable (notes, memories, rules, skills moved in) and a shared craft bindle read-only. Memories round-trip between machines through git, including from Windows.
- **Docs:** README (usage), docs/design.md (design), `/bindle` (how Claude in any session operates bindle), MIGRATION.md (what Claude follows to move a setup in), AGENTS.md (orientation for agents, including the rule that docs ship with each change), CHANGELOG.md.

## Next steps

**Standing requirement (2026-11-24):** everything bindle ships works on macOS, Windows and Linux. Unit tests run on all three in CI; anything CI can't reach (Claude Code's own behaviour, such as how it resolves paths) gets a manual check on a real machine of each OS before it's called done, and an assumption in the contract test (step 2).

**Done (2026-11-24, v0.29.0): `bindle global <name>`**, so a bindle's `rules.md` is always on: every folder and every subagent, not only folders where the bindle is attached. Built as planned below; the design and probe results are in docs/design.md ("Always-on rules"). Probed on macOS (Claude Code v2.1.331): absolute and `@~/` imports both load at user level, inside and outside the home folder, with no approval; spaces escaped as `\ ` work; an import from the system temp folder didn't load (cause unknown). Chosen form: absolute path, forward slashes, escaped spaces.
- **Manual checks before calling it done on each OS** (CI can't run Claude Code), each with the headless marker technique (a marker file imported by the user `CLAUDE.md`, a fresh `claude -p` session that also spawns a subagent):
  - Windows: `bindle global craft` writes `@C:/Users/<you>/…/rules.md` into `%USERPROFILE%\.claude\CLAUDE.md`, and it loads in the main session and a subagent.
  - Windows: a bindle path with a space loads; a CRLF `CLAUDE.md` stays CRLF; whether `@~/…` resolves there (informational: bindle writes absolute paths).
  - Linux: the import loads in the main session and a subagent.
  - Every OS: an interactive session shows no approval prompt for the import; the session check's pull of a global bindle finishes within its 30-second hook and its warnings show in the terminal.
- Why: hook output (`rules.md`, read-only memory indexes) reaches the main session only; subagents get `~/.claude/CLAUDE.md` (with its `@path` imports) and the writable bindle's memory index, but no hook output. Verified 2026-11-24 with context probes and a fresh headless session whose subagent saw an imported marker. So rules meant for every session and subagent belong in CLAUDE.md, and an `@path` import is the native way to put a bindle file there.
- `bindle global <name>` writes a marked block in `~/.claude/CLAUDE.md` holding `@<absolute path to the bindle>/rules.md`; `--off` removes it. Everything outside the block is the person's own and untouched (create the file if missing; keep the rest byte for byte).
- The hook skips injecting `rules.md` for a bindle that's imported globally, so it isn't loaded twice where that bindle is also attached.
- `doctor`: the import target exists; a warning when a global `rules.md` is large (every session and subagent pays for it); a note that CLAUDE.md changes apply from the next session (subagents get the session-start snapshot, not a fresh read).
- Staying current: a global bindle's rules load in every folder, but its own hook (and so its sync pull) runs only where it's attached. The plugin's session check, which runs in every session, pulls each globally imported bindle that has sync on (pull only: an `explicit`-writes bindle is never writable, so nothing is ever auto-committed or pushed to it), and warns in the terminal when one is behind its remote or the pull fails. `doctor` shows the same.
- Keep the name `rules.md` (not a CLAUDE.md in the bindle: a bindle's root CLAUDE.md is `@AGENTS.md`, guidance for maintaining the bindle itself, and would load as project instructions in sessions opened inside it).
- Cross-platform: block editing and the hook skip unit-tested on all three OSes; manual checks of how Claude Code resolves the import path on Windows (`C:/…`, `~`) and Linux. Contract-test assumption: "a user CLAUDE.md `@path` import reaches the main session and subagents".
- Then: README, `/bindle`, docs/design.md (always-on rules and why), CHANGELOG, release, `bindle update` on each machine.

**Planned (2026-11-24): onboarding (`/bindle-onboard`)**, to make setup easy; it becomes the basic demo, built from the person's real bindles. bindle-demo stays for the multi-domain walkthrough (promotion, private terms, notes between domains) and as the contract test's base.
- Offered by the session check when no bindles exist (one line, gone once a bindle exists; no state kept).
- First question: do you already have bindles? If yes: clone each into place (`~/bindles/<name>`, or `<domain>/.bindle`), attach, `global`, and skip creating.
- Otherwise: create craft and make it global; create a demo domain and attach craft to it; then "see it work": a session in the demo folder loads craft's rules but not the default memory folder's context (the person launches it, or a short headless `claude -p` shows it).
- Remotes: for each bindle, ask where it lives (a private personal repo, the employer's git, or local only) and give the commands; bindle never adds a remote itself. Outside onboarding: `doctor` warns when sync is on and there's no remote; the writable bindle's session text lets Claude offer help when backup or another machine comes up.
- Offer migration (declinable). For many repos (a domain with 20+ repos, each with its own memories), migrate in batches, tracked in a checklist in the new bindle's `notes/` (pending, done or skipped per repo), so it can stop and resume across sessions.
- Test: run it on a second macOS user account (a fresh `~/.claude` and `~/bindles`; a scratch `CLAUDE_CONFIG_DIR` starts logged out), which also covers most of the fresh-user test (road to 1.0, step 3). Comes before that test.

**Planned (2026-11-24): references between bindles.** One source of truth: a domain refers to craft rather than copying it, since craft is meant to be loaded everywhere (global). The rule: a domain may refer to craft, by name not path ("craft's rules"; paths differ per machine and move), and phrased so it still makes sense if craft isn't loaded; craft never refers to a domain (it would name the domain, and dangles wherever that domain isn't attached); domains never refer to each other (a general version goes to craft, a reminder to the other's inbox).
- The bindle template's `AGENTS.md` states the rule, so Claude follows it when writing memories (`AGENTS.md` isn't a managed file, so `upgrade` won't change an existing one; the CHANGELOG gives the line to add by hand, as 0.28.0 did).
- `doctor` warns when a bindle's files mention a path inside another bindle, and especially when craft (an `explicit`-writes or shared bindle) mentions a domain bindle.

**Order (2026-11-22):** the two remaining migration gaps below, then the demo repo and the contract test (road to 1.0, steps 1 and 2); then one thorough review of the whole repo (done 2026-11-23, an adversarial review; every finding fixed in v0.26.0); that's enough to hand to a friend for the fresh-user test. The owner's own setup waits until after.

Walkthrough run on another Mac with real sessions (2026-11-22). The warning about pulled code changes reached only Claude too; it shows in the terminal from v0.24.0. Found while building it, fixed in v0.21.0: commands that took a bindle only by path, and doctor's fixes printing paths instead of names. Originally planned: Fixtures plus a cross-platform `setup` script that builds everything in `~/bindle-demo/` without touching real bindles: an `acme/` project with a `demo-acme` bindle (fake memories, private terms, a skill naming Acme specifics) and an empty `demo-craft`; names carry `demo-` because bindle names are unique per machine. README walkthrough, one session per domain: recall a memory and run `/demo-acme:release-notes`; save a memory; promote the skill to demo-craft (see the private-terms check catch "Acme"); remove it from demo-acme, attach demo-craft read-only, and see `/demo-craft:release-notes` still work and an edit to craft refused; a second domain (`globex/`) gets the skill but none of acme's memories; send globex a note from acme; improve the skill from globex with `--replace`. A `cleanup` script undoes it all. The contract test reuses the setup, so a change that breaks the walkthrough fails.
2. **Guard against Claude Code changes.** bindle relies on Claude Code behaviour it doesn't control (settings at the repo root or launch folder, `autoMemoryDirectory`, directory marketplaces and `--scope local`, machine-wide marketplace names, hook events, environment and the 10k cap, a user-level SessionStart hook's `cwd` input and `systemMessage` output, `Edit(//path/**)` rules, plugin `.mcp.json`, per-folder memory keys).
   - Turn `tests/e2e.sh` into a contract test: one named check per assumption, each failure naming the assumption that broke.
   - Assumptions from `bindle global` (2026-11-24): Claude Code reads the user `CLAUDE.md` from `$CLAUDE_CONFIG_DIR`, else `~/.claude`; a user `CLAUDE.md` `@path` import (absolute, forward slashes, escaped spaces, outside the home folder too) reaches the main session and subagents with no approval prompt; relative links in an imported memory index resolve (main session and subagent open the linked file); hook output doesn't reach subagents; subagents get the session-start `CLAUDE.md`, not a fresh read. Keep the test's bindles out of the system temp folder (an import from there didn't load).
   - `bindle selftest`: run those checks in a scratch folder against the installed Claude Code (a few short sessions), clean up, report pass or fail per assumption. Friends can run it too.
   - `doctor` records the Claude Code version the last passing selftest ran on, and warns when `claude --version` differs.
   - docs/design.md "Claude Code constraints": link each assumption to its check.
   - Later, once public: a scheduled run (needs an API key as a repo secret; the owner's call).
3. **A fresh-user test:** someone follows only the README on a clean machine or account; fix what they trip on.
4. **Go public** (or add collaborators): the owner's step on GitHub. Then tag 1.0.

**Gaps found migrating a real setup (fix before 1.0):**
- Claude Code keeps one memory folder per launch folder, and on macOS each git repo is its own launch root. A domain folder holding several repos therefore has several old memory folders, and the domain-level attach doesn't reach sessions launched inside a repo. Done (2026-11-22): MIGRATION.md inventories every memory folder under the domain, maps per-repo memories to `projects/<repo>/`, treats files CLAUDE.md points Claude at (a lessons folder) as memory, and attaches the bindle to each repo the person launches from; the README explains launching from a repo. v0.18.0: `attach --repos` and `detach --repos` cover the domain folder and every repo directly inside it. v0.19.0: `doctor` warns about repos whose sessions would miss the domain's writable bindle. v0.20.0: the opt-in session check, recommended in the README's install section. All three sides of the gap are done.

**The owner's own setup (doesn't block 1.0):**
- Craft's `rules.md` takes over the live global instructions (`~/.claude/CLAUDE.md`), made always-on with `bindle global craft` on every machine; CLAUDE.md shrinks to machine-only lines plus the import block. Personal's `rules.md` then holds only personal-domain rules, including the boundary rule (work appears in personal only at a high, public level).
- Promotion pass at work (started 2026-11-24): general lessons and `craft`/`both` memories from the work bindle move to craft, rewritten; the first ones landed through `bindle promote` while craft was locked there (no extra permission rule needed). Memories that duplicate a global rule merge into the rule instead of being promoted. Craft is private for now (2026-11-22) while the workflow settles; once parts of it are ready to hand to others, make `craft-shared` (`--audience shared --writes explicit`) and promote those over.
- Later: a remote for the work bindle on storage the employer allows; delete the work machine's pre-bindle memory folder once the new setup has run for a while.
