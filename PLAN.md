# Plan

Where bindle stands and what's next. The design and the reasons behind it are in [docs/design.md](docs/design.md); what changed in each version is in [CHANGELOG.md](CHANGELOG.md). Update this when work lands or priorities change.

## Where it stands (2026-11-25, v0.37.1)

- **The tool:** the commands in README's table (tests keep the README, `/bindle` and AGENTS.md in step with the CLI); one Python implementation shared by the CLI and every bindle's hooks; unit tests in CI (macOS, Linux and Windows) plus an end-to-end test against real Claude Code.
- **In use on three machines:** a personal laptop and a Windows PC with the personal bindle writable; a work machine with its domain bindle writable (notes, memories, rules, skills moved in) and a shared craft bindle read-only. Memories round-trip between machines through git, including from Windows.
- **Docs:** README (usage), docs/design.md (design), `/bindle` (how Claude in any session operates bindle), MIGRATION.md (what Claude follows to move a setup in), AGENTS.md (orientation for agents, including the rule that docs ship with each change), CHANGELOG.md.

## Next steps

**Standing requirement (2026-11-24):** everything bindle ships works on macOS, Windows and Linux. Unit tests run on all three in CI; anything CI can't reach (Claude Code's own behaviour, such as how it resolves paths) gets a manual check on a real machine of each OS before it's called done, and an assumption in the contract test (step 1).

**Done (2026-11-24, v0.29.0): `bindle global <name>`**, so a bindle's `rules.md` is always on: every folder and every subagent, not only folders where the bindle is attached. Built as planned below; the design and probe results are in docs/design.md ("Always-on rules"). Probed on macOS (Claude Code v2.1.331): absolute and `@~/` imports both load at user level, inside and outside the home folder, with no approval; spaces escaped as `\ ` work; an import from the system temp folder didn't load (cause unknown). Chosen form: absolute path, forward slashes, escaped spaces.
- **Manual checks before calling it done on each OS** (CI can't run Claude Code), each with the headless marker technique (a marker file imported by the user `CLAUDE.md`, a fresh `claude -p` session that also spawns a subagent):
  - Windows: `bindle global craft` writes `@C:/Users/<you>/…/rules.md` into `%USERPROFILE%\.claude\CLAUDE.md`, and it loads in the main session and a subagent.
  - Windows: a bindle path with a space loads; a CRLF `CLAUDE.md` stays CRLF; whether `@~/…` resolves there (informational: bindle writes absolute paths).
  - Linux: the import loads in the main session and a subagent.
  - Every OS: an interactive session shows no approval prompt for the import; the session check's pull of a global bindle finishes within its 30-second hook and its warnings show in the terminal.
- Why: hook output (`rules.md`, read-only memory indexes) reaches the main session only; subagents get `~/.claude/CLAUDE.md` (with its `@path` imports) and the writable bindle's memory index, but no hook output. Verified 2026-11-24 with context probes and a fresh headless session whose subagent saw an imported marker. So rules meant for every session and subagent belong in CLAUDE.md, and an `@path` import is the native way to put a bindle file there.
- `bindle global <name>` writes a marked block in `~/.claude/CLAUDE.md` holding `@<absolute path to the bindle>/rules.md`; `--off` removes it. Everything outside the block is the person's own and untouched (create the file if missing; keep the rest byte for byte).
- The hook skips injecting `rules.md` for a bindle that's imported globally, so it isn't loaded twice where that bindle is also attached.
- `doctor`: the import target exists; a warning when a global `rules.md` is large (every session and subagent pays for it); a note that CLAUDE.md changes apply from the next session (subagents get the session-start snapshot, not a fresh read).
- Staying current: a global bindle's rules load in every folder, but its own hook (and so its sync pull) runs only where it's attached. The plugin's session check, which runs in every session, pulls each globally imported bindle that has sync on (pull only: an `explicit`-writes bindle is never writable, so nothing is ever auto-committed or pushed to it), and warns in the terminal when one is behind its remote or the pull fails. `doctor` shows the same.
- Keep the name `rules.md` (not a CLAUDE.md in the bindle: a bindle's root CLAUDE.md is `@AGENTS.md`, guidance for maintaining the bindle itself, and would load as project instructions in sessions opened inside it).
- Cross-platform: block editing and the hook skip unit-tested on all three OSes; manual checks of how Claude Code resolves the import path on Windows (`C:/…`, `~`) and Linux. Contract-test assumption: "a user CLAUDE.md `@path` import reaches the main session and subagents".
- Then: README, `/bindle`, docs/design.md (always-on rules and why), CHANGELOG, release, `bindle update` on each machine.

**Planned (2026-11-24): references between bindles.** One source of truth: a domain refers to craft rather than copying it, since craft is meant to be loaded everywhere (global). The rule: a domain may refer to craft, by name not path ("craft's rules"; paths differ per machine and move), and phrased so it still makes sense if craft isn't loaded; craft never refers to a domain (it would name the domain, and dangles wherever that domain isn't attached); domains never refer to each other (a general version goes to craft, a reminder to the other's inbox).
- The bindle template's `AGENTS.md` states the rule, so Claude follows it when writing memories (`AGENTS.md` isn't a managed file, so `upgrade` won't change an existing one; the CHANGELOG gives the line to add by hand, as 0.28.0 did).
- `doctor` warns when a bindle's files mention a path inside another bindle, and especially when craft (an `explicit`-writes or shared bindle) mentions a domain bindle.

**Done (2026-11-25, v0.36.1): Claude explains bindle well.** Measured: before, a fresh `claude -p "what is bindle?"` in an unrelated folder covered git-portable and promotion, but not guarded boundaries or the domain level; after, all four parts. Today a session sees only `/bindle`'s description ("carries … between machines in git repos", part one), and "The model" in `commands/bindle.md` explains the mechanics but not the why.

**Done (2026-11-25, v0.36.0): machine awareness.** Open questions decided (David, 2026-11-25): a named machine gets the block even with no global bindle; the session check rewrites a stale line (doctor compares with the line as written); `bindle machine [<name>]` plus a one-time ask from the session check. - **A machine name, per machine:** stored in `~/bindles/registry.json` (bindle's only per-machine state; never in a bindle, which would sync it everywhere). - **Delivered through the user `CLAUDE.md`, not hook output:** the session check is silent unless something's wrong, its `systemMessage` would show the line in the terminal every session, and hook output doesn't reach subagents. The user `CLAUDE.md` is per-machine and reaches every session and subagent, so bindle writes one line into its marked block: `This machine: work-mac (MacBookPro18,3, arm64, macOS 26.3)`, refreshed by the session check when the hardware or OS changes. Open: whether to write the block when no bindle is global, and how the "block isn't what this bindle writes" check treats the new line.

- Cross-platform: detection unit-tested on all three OSes; manual check that the line reaches a subagent on Windows and Linux. Contract-test assumption: the user `CLAUDE.md` block's plain text reaches the main session and subagents.

**Done (2026-11-25, v0.35.0): sync pushes craft, never commits it.** Found in real use: a spec file was written into craft from a folder where only personal was writable and committed by hand; `sync --all` said only "craft: pulled", which hid the uncommitted edits. Decided (David, 2026-11-25): craft is the toolset he carries everywhere, so committing to it stays deliberate, but sync should push what was committed.
- **Push existing commits:** for an `explicit`-writes bindle, sync pushes local commits (through `push_leftovers`, with its secret check) and never runs `git add` or `git commit`. Before, `sync_pull` never pushed a read-only bindle. Built as `push_explicit` in the hook, called by `bindle sync`, `sync --all`, the hook's session start and the global session check; the "pull only" line under `bindle global` above is superseded.
- **Warn on uncommitted edits:** sync and the session check say "craft: N uncommitted change(s), not committed by sync; commit them on purpose" instead of a bare "pulled".
- Unit-tested on all three OSes: pushes commits, leaves the working tree uncommitted, and the warning names the count.
